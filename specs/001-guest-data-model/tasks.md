# Tasks: Guest, Invitation, and Communication Data Model

**Input**: Design documents from `/specs/001-guest-data-model/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Tests**: Required. Constitution Principle I (test-first) and II (every table and policy has a database test proving what each role can and cannot do) make tests mandatory, so every story starts with test tasks that must fail before the implementation tasks begin.

**Organization**: Tasks are grouped by user story so each can be implemented and tested on its own.

**Manual prerequisites**: Account and dashboard setup that cannot be done from code (Resend domain and webhook, Supabase auth hook, Vault secrets, hosting) is tracked in https://github.com/cmhac/wedding-website/issues/3. Nothing in the automated tasks needs it except the real sends in User Story 5 and the production auth hook in User Story 2.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on unfinished tasks)
- **[Story]**: Which user story the task belongs to (US1 to US8)
- Migration files are created with `npx supabase migration new <name>`, which supplies the `<timestamp>` prefix
- `src/types/database.ts` is generated by `npm run db:types` and never hand-edited

## Path Conventions

Single Next.js project with `supabase/` beside it, as in `plan.md`: `src/app`, `src/components`, `src/lib`, `emails/`, `scripts/`, `supabase/migrations`, `supabase/tests/database`.

## Dependencies & Execution Order

### Phase dependencies

- **Setup (Phase 1)**: no dependencies.
- **Foundational (Phase 2)**: depends on Setup; blocks every user story.
- **User Stories (Phases 3–10)**: depend on Foundational. US1 through US4 are P1, US5 through US7 are P2, US8 is P3.
- **Polish (Phase 11)**: depends on the stories being delivered.

### User story dependencies

- **US1**: needs only Foundational. It is the MVP.
- **US2**: needs Foundational; reads the guests and invitations US1 creates, but can be tested with seed data.
- **US3**: needs Foundational and, for the guest meal UI, the RSVP form from US2.
- **US4**: needs Foundational; its guest-facing labels extend the RSVP form from US2.
- **US5**: needs Foundational; audience filters use the views from US3 and US4 (`household_rsvp_progress`, meal state), so build it after those.
- **US6**: needs US3 (meal views) and US4 (progress view).
- **US7**: needs Foundational (staff table and policies already exist); can run any time after, and is easiest to verify once US1 and US5 exist.
- **US8**: independent; may run in parallel with anything.

### Within each story

1. Write the tests and see them fail.
2. Write the migration or code that makes them pass.
3. Regenerate `src/types/database.ts` after any migration (never hand-edit).
4. Build the UI.
5. Run the quickstart scenarios named in the story.

### Parallel opportunities

- Tasks marked [P] touch different files and can run together.
- All test-writing tasks within a story are [P].
- US8 can proceed alongside any other story by a second person or agent.
- After US2, the US3 and US4 UI work can proceed in parallel since they touch different components.


## Implementation Strategy

### MVP first

1. Complete Setup and Foundational.
2. Complete US1 (guest list). Stop and validate: the couple can already replace their spreadsheet.
3. Add US2 (RSVP) for a usable guest-facing flow, then US3 and US4 to finish the P1 scope.

### Incremental delivery

1. Foundation → US1: the list.
2. US2: guests respond.
3. US3 and US4: meals and optional events.
4. US5: sends (needs the manual Resend and Supabase setup in issue #3 before anything real is sent).
5. US6 and US7: dashboard and planner.
6. US8: public pages, any time.

### Notes

- Every task that adds a table or policy also adds a pgTAP test proving what anon, guest, and staff can and cannot do (Constitution II).
- Fixtures and seed data are fake only (Constitution III).
- Commit after each task or small group. Tests must never be skipped or disabled to get green.
- Nothing real is emailed until the sending domain is verified (decision 0007).
