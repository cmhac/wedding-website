# Wedding Website Constitution

## Core Principles

### I. Test-First (NON-NEGOTIABLE)

Tests MUST be written or changed before the implementation they cover. Work follows
red, green, refactor: a failing test first, the minimum code to pass it, then cleanup with the
suite green. Tests live in `__tests__` directories next to the source and are named
`{name}.test.ts(x)`. Every new component, route handler, and database policy MUST have tests
that cover both success and error paths.

Rationale: this site handles guest RSVPs and sends email to real people. Mistakes are visible
to family and friends and cannot be unsent, so behavior is pinned down before it is built.

### II. Schema by Migration, Row-Level Security Everywhere

The database MUST change only through files in `supabase/migrations/`, created with
`npx supabase migration new <name>`. The database MUST NOT be edited by hand. Every table MUST
have row-level security enabled, with policies written for the least access each role needs
(guest, admin, anonymous). Policies MUST be covered by database tests that prove both what a
role can do and what it cannot (for example, one guest cannot read another guest's party).
`src/types/database.ts` is generated by `npm run db:types` and MUST NOT be hand-edited.

Rationale: Supabase exposes the database as an API, so row-level security is the access
control, not an extra layer on top of one.

### III. Secrets and Guest Data Stay Protected

`SUPABASE_SERVICE_ROLE_KEY` and `RESEND_API_KEY` are server-only. They MUST NOT be imported in
client components, MUST NOT carry a `NEXT_PUBLIC_` prefix, and MUST NOT be committed. Real
values live in `.env.local` or the hosting environment; `.env.example` documents the names
only. Guest data (names, emails, addresses, dietary needs, RSVP answers) is personal data. It
MUST NOT be written to logs, and test fixtures and seed data MUST use fake data only.

Rationale: the service role key bypasses row-level security, and the guest list is the most
sensitive thing this site holds.

### IV. One Repository for Everything

The website frontend, backend code, database schema and tests, email templates and sending
logic, scripts, and documentation MUST live in this repository, in the locations defined in
`CLAUDE.md`. Email designs are code (React Email templates in `emails/`), previewed with
`npm run email:dev`, and reviewed like any other change. Work that cannot live here, such as
dashboard-only configuration, MUST be documented in `docs/`.

Rationale: a single repository keeps the schema, the API, the emails, and the pages that
depend on them changing together.

### V. Current Tooling, Recorded Decisions

Tools and dependencies MUST track their newest release unless the ecosystem blocks it. Each
exception (for example, TypeScript pinned below 7 until `typescript-eslint` supports it) MUST
be recorded in `docs/decisions/` with the condition for revisiting it. Architecturally
significant decisions, including each item under "Open decisions" in `docs/architecture.md`,
MUST be recorded as a file in `docs/decisions/` once settled.

Rationale: this repository intentionally starts from current versions rather than inheriting
older ones, and unrecorded exceptions get "fixed" later and break the toolchain.

## Technology Stack and Constraints

- **Frontend:** Next.js (App Router), React, TypeScript (strict), Tailwind CSS.
- **Backend:** Supabase for Postgres, Auth, API, and Edge Functions.
- **Auth:** magic-link sign-in for everyone, the couple and guests alike.
- **Email:** Resend for delivery, React Email for templates.
- **Tests and quality:** Jest with React Testing Library, ESLint (flat config), Prettier,
  Husky, and lint-staged.
- **Package manager and runtime:** npm; the Node version in `.nvmrc`.
- Choices beyond this list (hosting, where email sends run, the guest and household data
  model, admin authorization) are open decisions in `docs/architecture.md`. Until they are
  recorded, a plan MUST NOT silently assume one.
- Generated files MUST NOT be hand-edited or reformatted: `.specify/`, `.claude/skills/speckit-*`,
  and `src/types/database.ts`.

## Development Workflow and Quality Gates

- Before pushing, `npm run format:check`, `npm run lint`, `npm run type-check`, and `npm test`
  MUST pass. The pre-push hook runs lint, type-check, and tests; CI runs all four plus the
  build once the app has routes.
- Features follow the Spec Kit workflow: `/speckit-specify`, `/speckit-plan`,
  `/speckit-tasks`, then `/speckit-implement`. Each plan MUST pass the Constitution Check
  against this document, and any violation MUST be justified in the plan's complexity table.
- Tests MUST NOT be skipped, disabled, or deleted to make a check pass.
- Documentation (`README.md`, `CLAUDE.md`, `docs/`) MUST be updated in the same change that
  alters the behavior or conventions it describes.

## Governance

This constitution governs development practice for this repository. Where it conflicts with
other guidance, it prevails; `CLAUDE.md` provides runtime guidance for day-to-day work and
MUST stay consistent with it.

- **Amendments:** change this file with `/speckit-constitution` and merge the change through
  review. Each amendment MUST update the version, the amended date, and any templates or docs
  that it makes stale.
- **Versioning:** semantic. MAJOR for removing or redefining a principle in a backward
  incompatible way, MINOR for adding a principle or section or materially expanding guidance,
  PATCH for clarifications and wording fixes.
- **Compliance:** reviews and plans MUST verify compliance with these principles. Complexity
  or deviation MUST be justified in writing in the plan or the pull request.
