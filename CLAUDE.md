# Wedding website

Chris and Hannah's wedding website. This repo holds everything: the website
frontend, backend code, database schema, email sending logic (email content is supplied separately), and
docs. See [docs/architecture.md](docs/architecture.md) for the plan and the
recorded decisions.

## Stack

- Next.js (App Router), React, TypeScript, Tailwind CSS
- Supabase: Postgres, Auth (magic links for couple and guests), API, Edge Functions
- Resend for email delivery; email templates (React Email suggested) are written by others and registered in `emails/index.ts`
- Jest + React Testing Library, ESLint (flat config), Prettier, Husky + lint-staged
- npm

## Scope

This repository's work is **backend only**. Do not build any screen or visual component: not the public site, not guest-facing screens (including RSVP), and not admin screens. The couple's designer owns visual design, and the screens are built separately against two documented interfaces: the guest API (`src/app/api/guest`, contract in `specs/001-guest-data-model/contracts/guest-api.md`) and the admin API (direct data access under row-level security plus `src/app/api/admin`, contract in `specs/001-guest-data-model/contracts/admin-api.md`). Email content is out of scope too: write no subject lines, copy, or email designs, and no templates (the template interface is `specs/001-guest-data-model/contracts/email-templates.md`). Do not add a design system, theming, or UI components. If a task seems to need a screen or visual design, stop and ask.

## Conventions

- **Test-driven development.** Write or change tests before implementation.
  Tests live in `__tests__` directories next to the source and are named
  `{name}.test.ts(x)`. Run `npm test`.
- **Schema changes go through migrations.** Never edit the database by hand;
  add a file under `supabase/migrations/` (`npx supabase migration new <name>`).
  Every table gets row-level security.
- **Secrets.** `SUPABASE_SERVICE_ROLE_KEY` and `RESEND_API_KEY` are server-only.
  Never import them in client components or prefix them with `NEXT_PUBLIC_`.
  Copy `.env.example` to `.env.local`; `.env*` is gitignored.
- **Guest data is personal data.** Don't log emails or addresses, and keep
  fixtures fake.
- **Plain-English references.** Never refer to a task, issue, decision record,
  finding, or any other placeholder or ID number (T001, #4, 0003, FR-018, D1)
  without saying in plain English what it is. Name the thing first ("the
  hosting decision", "the task that checks the decisions are confirmed"), and
  add the ID only as a pointer afterwards. This applies to chat replies,
  commit messages, issues, and docs.
- **Before pushing:** `npm run format:check && npm run lint && npm run type-check && npm test`.
  The pre-push hook runs lint, type-check and tests.

## Spec-driven development

[Spec Kit](https://github.com/github/spec-kit) (`specify-cli` 1.2.1, Claude
integration) is set up. Skills live in `.claude/skills/speckit-*` and shared
files in `.specify/`; both are generated, so don't hand-edit or reformat them
(Prettier ignores them, and `.specify/integrations/*.manifest.json` tracks file
hashes). Workflow, per feature:

1. `/speckit-constitution`: project principles, in `.specify/memory/constitution.md`
2. `/speckit-specify`: what and why (optional `/speckit-clarify` before planning)
3. `/speckit-plan`: technical plan
4. `/speckit-tasks`: task list (optional `/speckit-analyze`)
5. `/speckit-implement`: build it, following the TDD convention above

Upgrade with `uv tool install specify-cli==<version>` then
`specify init --here --force --integration claude` on a clean branch, and review
the diff.

## Commands

```bash
npm run dev          # Next.js dev server
npm run email:dev    # React Email preview server (for templates supplied by others)
npm run db:start     # local Supabase (needs Docker)
npm run db:reset     # re-apply migrations and seed.sql
npm run db:types     # regenerate src/types/database.ts
npm run test:db      # pgTAP database tests (needs local Supabase running)
```
